# Three.js 3D 桌游开发

## 何时用

- 新建或改造 Three.js 场景、相机、光照、材质
- 接入 glTF/GLB 模型与纹理，或做资源体积压缩
- 实现鼠标/触摸拾取、拖拽落子、相机控制
- 把棋类规则接入渲染层，或排查"画面对了但规则错了"
- 排查掉帧、显存增长、移动端发热

不适用：纯 2D DOM 界面、服务端逻辑、与 Three.js 无关的构建问题。

## 一、分层：规则与渲染必须分离

这是本类项目最容易翻车的地方，先立规矩再写代码。

```
core/    纯规则：棋盘状态、走子合法性、回合机、胜负判定   —— 零 three.js 依赖
render/  Three.js：场景、网格、材质、动画、相机           —— 不写规则
input/   指针/键盘 → 意图（"把棋子从 A 移到 B"）           —— 不直接改状态
ui/      面板、按钮、结算层
```

判据（写完自查）：

- 删掉整个 `render/`，`core/` 的单元测试仍能全绿
- 任意一条规则能用一个不渲染的纯函数测试
- 渲染层不知道"什么是合法走法"，只负责把状态画出来

## 二、场景与相机

1. 桌游用**透视相机 + 有限俯角**（30°–60°）比纯正交更有立体感；需要绝对公平的对位时再切正交。
2. 相机用 `OrbitControls` 起步，但**限制极角与距离**，禁止自由翻滚到棋盘背面：
   ```ts
   controls.minPolarAngle = Math.PI / 6;
   controls.maxPolarAngle = Math.PI / 2.2;
   controls.enablePan = false; // 棋盘固定居中，避免玩家把棋盘拖丢
   ```
3. 棋盘尺寸统一用**世界单位格子**（1 格 = 1 单位），所有落子坐标由 `gridToWorld(x, y)` 单点换算，禁止散落魔法数。
4. 光照用 `HemisphereLight` + 一盏带阴影的 `DirectionalLight` 即可；阴影贴图按需开，移动端先关。
5. 相机切换（全局视角/近距离观察）用补间而不是瞬移，否则玩家会丢失空间感。

## 三、资源管线

- 格式优先级：**GLB > glTF + 外链 bin > 其他**。GLB 单文件、易缓存、少一次请求。
- 压缩：几何用 **Draco** 或 meshopt，纹理用 **KTX2(Basis)** 或 WebP。压缩后必须实测首屏时间，不能只看文件大小。
- 加载用 `GLTFLoader` + `LoadingManager` 统一进度；大资源在进入对局前预加载完，不要在落子瞬间卡住。
- 卸载：场景切换时对每个 geometry / material / texture 调 `dispose()`，并从 `scene` 中 `remove()`。**不 dispose 是显存泄漏的头号原因。**
- 同一个模型实例化多个棋子时用 `InstancedMesh` 或克隆后共享 geometry+material，不要重复解析文件。
- 资源许可：只接 CC0 或已明确授权的资源，登记来源与许可（见 `agent.md` §8）。不确定就换资源，不要赌。

## 四、拾取与输入

1. 落子交互用 `Raycaster`，**只对可交互层做检测**：把棋子/格点放进单独数组或 `Layers`，不要对全场景 `intersectObjects(scene.children)`。
2. 拾取用**粗粒度命中体**（棋盘格用一个不可见的平面/盒子代理），不要用高面数模型做碰撞。
3. 触摸端 `pointerdown` 同时服务鼠标与触摸，别写两套；区分"点击"与"拖动旋转"用位移阈值 + 时间阈值。
4. 悬停高亮、合法落点预演这类反馈属于 `render/`，但**合法点集合由 `core/` 算出来传进来**。
5. 所有输入最终变成一个**意图对象**交给规则层：`{ type: 'move', from, to }`。规则层校验失败时返回原因，UI 负责提示。

## 五、回合制棋类的状态与回放

- 状态机显式化：`idle → 选子 → 预演 → 确认 → 结算 → 换手`。不要用布尔量拼状态。
- 状态用**不可变快照**（每次走子产生新状态），悔棋 = 弹栈，不需要反向运算。
- 随机性（洗牌、掷骰）走**带种子的 PRNG**，种子进对局记录。这样复盘、联机同步、Bug 复现都免费得到。
- 动作日志（action log）与状态快照二选一即可，但**必须有**：没有日志就无法复现玩家报的 Bug。
- 计时器、回合上限这类规则放 `config`，不要硬编码在逻辑里。

## 六、性能预算

先定预算，再优化；超了就是 Bug。

| 项 | 桌面 | 移动 |
| --- | --- | --- |
| 帧率 | 60 fps | ≥ 30 fps |
| Draw call | < 150 | < 60 |
| 三角形 | < 300k | < 100k |
| 首屏可交互 | < 2 s | < 4 s |
| 纹理单张 | ≤ 2048² | ≤ 1024² |

排查顺序：先看 draw call，再看三角形，最后才怀疑着色器。合批、`InstancedMesh`、共享材质、关闭不必要的阴影，通常能解决八成问题。

## 七、验证方式（每条改动都要过）

- 规则改动：`core/` 单测通过（含非法走法必须被拒的用例）
- 渲染/交互改动：在真实浏览器里点一遍受影响的流程，看控制台无报错
- 性能相关改动：`renderer.info.render.calls / triangles` 改动前后各记一次
- 资源改动：Network 面板确认体积与 404，切换场景后确认显存回落

## 八、常见错误清单

- 在 `render/` 里写 `if (isValidMove())` —— 分层已破，改回去
- 用 `setInterval` 驱动动画 —— 用 `requestAnimationFrame` / `renderer.setAnimationLoop`
- 每帧 `new THREE.Vector3()` —— 复用临时对象
- 切换场景不 dispose —— 显存随时间线性上涨
- 落子逻辑依赖帧率或 `deltaTime` —— 回合制逻辑不应依赖时间
- 监听器不摘（`addEventListener`、`ResizeObserver`）—— 切场景后重复触发
